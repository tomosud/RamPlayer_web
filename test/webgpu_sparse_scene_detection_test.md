# WebGPU疎サンプリング式カット検出：実行手順と実測結果

## 手動テスト

`test/run_scene_detection_test.bat` をダブルクリックする。最新のテストページをビルドし、`http://localhost:8124/cut-test.html` を自動で開く。終了時はBATのウィンドウで `Ctrl+C` を押す。

開発サーバーを使う場合は、リポジトリのルートで次を実行する。

```bash
npm run dev
```

ChromeまたはEdgeで `http://localhost:5173/cut-test.html` を開き、動画、モード、解析グリッド、閾値を選択して「解析開始」を押す。

選択できる解析方式:

- GPU・全フレーム
- CPU・全フレーム
- GPU・二段階: 全体を粗間隔で解析し、候補区間だけ細間隔で再解析
- CPU・二段階: GPU版と同じ二段階アルゴリズムをCanvas 2Dで比較

解析完了後、候補時刻をクリックすると動画が1秒前から再生される。各候補を「正しい」「誤検出」「未判定」に分類し、目視判定を含む結果JSONをコピーできる。解析中は中止でき、中止後も同じページから再実行できる。正式な比較では各条件を3回以上実行し、経過時間の中央値を使用する。

## 動作条件と既知の制限

- 最新のChromeまたはEdge、WebCodecs、WebGPU対応GPUが必要
- WebGPU非対応時にCPUモードへ自動フォールバックしない
- WebGPU経路ではCanvas、`getImageData()`、`VideoFrame.copyTo()`を使用しない
- GPUからCPUへは256フレーム単位でスコアバッファだけを読み戻す
- 回転はブラウザが提示するVideoFrameの向きに従う
- 実機で`r16float`のstorage書き込みが非対応だったため、輝度テクスチャには`r32float`を使用
- VideoFrameの寿命を保証するため、16フレーム単位でGPU完了を待って解放する。この同期は現在のWebGPU計測時間に含まれる

## 2026-07-18 実測

対象動画:

- 長さ: 367.301秒
- 解像度: 3840×1644
- コーデック: AV1 (`av01.0.12M.08`)
- デコードフレーム数: 8,815
- 解析グリッド: 64×36
- カット閾値: 10

| モード | 経過時間 | 実効fps | 実時間倍率 | カット候補 |
| --- | ---: | ---: | ---: | ---: |
| `decode-only` | 34.20秒 | 257.7 | 10.74倍 | 0 |
| `webgpu-sparse-sad` | 72.15秒 | 122.2 | 5.09倍 | 235 |
| `cpu-canvas-64x36` | 91.61秒 | 96.2 | 4.01倍 | 235 |

この1回の計測ではWebGPU版はCPU Canvas版より約21%短時間だった。WebGPU版とCPU版は候補時刻が一致し、主要なスコアも概ね小数第2～3位まで一致した。一方、閾値10では235件となり過検出気味なので、検出品質評価では閾値を調整する必要がある。

この数値は各モード1回の参考値であり、中央値ではない。GPUExternalTextureの実際のメモリ経路やゼロコピー動作はJavaScriptから確認できないため断定しない。

## 2026-07-18 二段階GPU実測

同じ動画を64×36、最終閾値20、粗間隔0.5秒、細間隔0.1秒で解析した。

- 総時間: 99.20秒
- 粗解析: 60.95秒、735枚
- 細解析: 38.19秒、1,614枚
- 合計処理枚数: 2,349枚
- 実時間倍率: 3.70倍
- 近接候補抑制後: 83件

処理対象として返されたフレーム数は全フレーム版より少ないが、このAV1動画では指定時刻取得でもキーフレーム間の内部デコードが必要になる。粗解析後に細解析でもう一度動画を走査するため、今回の条件では全フレームGPUの72.15秒より遅かった。二段階方式が常に高速になるとは限らず、コーデック、キーフレーム間隔、候補区間数に依存する。
